# 结构化操作跑团平台：完整实施计划

日期：2026-09-13；状态：实验分支实施规格，未实现、未授权发布。

配套执行提示词：`KIMI_BACKEND_PLATFORM_TASK_20260913.md`（后端）与 `ZCODE_FRONTEND_PLATFORM_TASK_20260913.md`（前端）。默认 Kimi 做后端、zcode 做前端；人员可交换，职责与协议保持不变。

本文细化并更新 `KEEPER_PLATFORM_HARNESS_DESIGN_20260913.md`，出现差异时以本文为准。不是仅修改按钮样式，也不是一次性推翻所有旧玩法。

## 1. 产品目标与完成定义

玩家通过按钮选择对象和操作，形成明确行动请求。Agent 或人类守秘人判断情境、请求检定、调用游戏命令、解释结果。平台负责授权、确定性计算、状态与事件持久化。

自然语言保留为自由扮演、交谈、补充做法和快捷意图入口。按钮请求不能先拼成自然语言，再依赖正则恢复动作与目标。自由文本本身不直接改变世界；Agent 将其解释成明确命令或交谈回应。

完整交付必须同时满足：

1. 出示、使用、前往、普通掷骰和被请求检定均有实际可用入口。
2. Agent 能根据结构化请求主持，遇到玩家选择停止；明确工具结果是后续叙事依据。
3. 人类守秘人使用同一组操作，可在完全不配置模型时完成最小调查流程。
4. 本地、云端单人、云端多人使用同一协议和组件；后台能力必须在对应前端暴露。
5. 私人信息不泄露；重试不重掷、不重复扣物或移动；刷新和恢复不丢待办。
6. 旧世界可继续走旧模式；实验模式明确启用，不静默改变所有用户节奏。

不纳入本轮：运营后台、自动生产发布、微服务/K8s、语音视频、战棋地图、通用规则系统、完整多人分队模拟、任意文件工具。现有 CoC 规则、数据库、模组和素材优先复用。

## 2. 已核对的起点与改造点

- `frontend/src/investigator-actions.ts` 当前 `submitPanelAction` 调用 `sendAction(buildPanelActionText(draft))`；必须替换新模式的这条路径。
- 物品主要仍是字符串标签，线索 key 可由类别/文本拼接；不能直接作为新的可写实体 ID。
- `src/gameplay/discovery.py` 与 `action_resolution.py` 会由调查目标推断抵达；新模式禁用这种无主持决定的自动移动。
- `src/app/agent_graph.py` 目前围绕预结算与叙事构造；新模式需要可暂停、恢复的工具循环。
- `src/ai/tools/registry.py` 已有确定性 handler，但不适合直接开放为任意工具 HTTP 接口。
- `GameEngine.handle_action` 使用回合缓存，权威结果可能在最终持久化前公开；不能直接把此模式当作逐工具提交的保证。
- 现有成员 role 为 owner/player/viewer，需要独立 keeper 授权，不把房主与守秘人混同。
- 现有模型就绪门禁不能挡住 human 房间；也不能因此放开 agent 房间的平台 Key 兜底。
- 当前工作区正在变更场景指示器、过渡修复和多人恢复。实现开始前记录基线并协调文件所有权，不覆盖这些改动。

## 3. 产品交互规格

### 3.1 线索卡：说明、展示与交付分开

线索分类、收起、展开沿用现有卡片。点击“出示”打开编辑器：已选线索、目标人物、方式、可选询问。

- “说明内容”：将已知信息告诉目标，不要求拥有实物。
- “展示图片”：需该线索有玩家已获准查看的素材。
- “展示原件”：需选择玩家实际持有的关联物品。
- 默认不转移所有权、不消耗物品。“交给对方”如实现，应独立明确操作与确认，不由出示暗含。

目标优先从已知且可交互的在场 NPC/调查员列表选择，以 ID 提交。未知目标允许“描述其他对象”，提交未解析文本供主持澄清，不能强选一个 NPC。选择面板只使用玩家公开投影。

### 3.2 道具卡：使用请求

点击“使用”带入物品 ID、可用数量与支持的常见用法；玩家选择目标和数量，可写其他做法。已知用法提交 operation 枚举；即兴用法使用 custom + 文本，由主持判定。

提交不等于扣减。Agent 判断是否可尝试、是否需要检定、代价何时发生；领域工具在明确执行时扣减。允许“消耗了药品但检定失败”这类规则结果，不能把所有失败都写成零代价。未执行则不扣减，除非另有已明确执行的前置代价。

### 3.3 场景指示器与移动

保留左上角“当前场景 · …”，由服务端已提交的公开状态更新。增加独立“前往…”入口，仅列已知可选目的地；不泄露完整秘密地图。

点击具体目的地代表明确提出现在出发，可当轮判断、执行和叙事；不能每次再问同一问题。“我想看看尸体”属于文本意愿，默认先回应与说明安排，不因目标在异地自动移动。“那就过去”可由 Agent 根据最近明确约定目的地承接；歧义时问一次。

抵达不等于调查：进医学院不能自动检查尸体、取得物证或结算对应 SAN。过渡可以在移动命令后演出；需要玩家决定时形成真实暂停点，不能靠一句劝留后继续替玩家出发。

### 3.4 骰子

游戏工具区新增“掷骰”入口，提供常见骰型与受限表达式；后端限制骰子个数、面数、修正值和请求频率。普通骰结果注明“普通掷骰”，不自动发线索、扣 SAN、触发检定成功分支，也不能用它绕过重复检定门禁。

主持请求检定后，聊天区/待办区显示持久检定卡：调查员、技能、难度、奖惩骰、公开可知的尝试描述与已知代价，按钮“掷骰”“放弃”。仅指定玩家可执行；其他可见玩家只读。

按钮不能修改难度、技能值、奖惩骰或结果；后台从已保存检定请求和权威角色状态取值。普通技能检定公开自身技能值；秘密检定的细节与结果按主持可见性投影，玩家只知道获准知道的内容。

按钮确认后服务端生成一次结果，再播动画；动画失败直接显示原结果。孤注一掷必须新建与原结果关联的检定请求，校验规则与新做法，不能出现普通“重掷”按钮。

### 3.5 操作状态与错误体验

卡片呈现：待提交 → 主持处理中 → 等你回应/掷骰 → 已完成/未执行/已取消/需要重新确认。具体故事行动成功与否由结果正文说明，不把“服务器收到了请求”显示成行动成功。

断线时保留草稿，刷新恢复待办。提交超时先查询原请求状态，重发沿用同一 request_id，不重新创建行动。对象已失效时解释原因并刷新候选，不能静默改目标。

Agent 不可用时请求标记为暂停/可恢复；已经执行的工具结果保留，允许主持接管，不整轮重跑。

## 4. 角色、运行模式与边界

维护房间管理角色与玩法能力两个维度。keeper 能看主持资料、处理玩家意图；owner 负责房间和计费管理，不自动看秘密。服务端验证调查员控制关系，不能相信客户端 principal。

世界新增明确的 execution_profile（例如 legacy / structured_v1）和主持模式 human / assisted / agent。首版 legacy 完全保留现有路径；structured_v1 才切换新协议、命令和结算语义。human 不初始化模型，也不自动调用摘要。assisted 草稿仅主持可见，经人类批准才执行；agent 在授权内自主执行。

单一活动主持控制权带 controller_epoch。接管递增 epoch，使旧模型任务和迟到调用无权执行。取消网络请求不能代替控制权撤销。客户端断开不自动取消已提交行动或删除角色。

本地与云端同功能；匿名单窗口本地不承诺跨设备隐私。局域网真人房间须启用账号或房间会话凭证，不能直接扩大当前匿名服务监听范围。

## 5. 前后端共用协议（后端先冻结）

以下为规范草案；后端在第一里程碑生成正式 schema 与固定 fixtures。字段发生变更必须同时更新契约文件、前端类型和 fixtures，不能双方自行猜。

### 5.1 客户端行动请求

```json
{
  "type": "action_request",
  "protocol_version": 1,
  "request_id": "uuid",
  "world_id": "world-id",
  "expected_revision": 12,
  "investigator_id": "investigator-id",
  "action": {
    "kind": "present_clue",
    "clue_id": "clue-id",
    "presentation": "describe",
    "physical_item_id": null,
    "target": {"kind": "npc", "id": "npc-id"},
    "question": "你认得这份证明吗？"
  }
}
```

action 是 discriminated union：

| kind | 参数 |
|---|---|
| present_clue | clue_id、presentation(describe/image/original)、physical_item_id?、target、question? |
| use_item | item_id、quantity、operation、target?、approach? |
| move | destination_scene_id |
| freeform | text；由主持解释，无自动关键词状态写入 |

target 是 npc/investigator/scene_object 的稳定 ID，或 unresolved + text；服务端未解析目标不直接执行对应命令。没有值的可选字段以正式 schema 定义为准。

普通骰走独立 `free_roll_request`（request_id、world_id、investigator_id、spec），不消耗模型额度；检定按钮走 `check_response`（request_id、world_id、check_request_id、decision=roll/decline）。检定参数已存服务端，不随按钮提交。

客户端不发送 authority/principal/controller_epoch 来授予自己权限；epoch 是服务端对主持调用的授权绑定。expected_revision 冲突返回明确 conflict，需刷新后用户重新提交或由主持重新判断，不静默执行过期计划。

### 5.2 后端事件

公共事件信封：protocol_version、event_id、world_id、sequence、revision、type、cause_request_id、payload。revision 表示已提交世界版本；纯消息不必增加世界 revision，但仍有独立事件顺序。可见性在服务端过滤后投递，不把完整接收人列表或私密载荷广播给无权用户。

必须提供：action_ack、action_status、check_requested、check_resolved、check_cancelled、roll_resolved、message_started/chunk/completed、scene_changed、clue_granted、inventory_changed、state_changed、request_error、session_snapshot。

`action_ack` 仅代表请求已持久接收。行动状态枚举：queued、processing、awaiting_player、completed、declined、cancelled、paused、failed。completed 代表主持已完成处理，不代表故事行动必然成功；领域结果另列 success/failure/not_executed。

message 的 speaker 使用 keeper/npc/investigator/system + 合法 ID，audience 由服务端授权解析。普通玩家只能以自己身份发言；主持不能伪造玩家已选择的行动。新消息直接使用结构身份，旧 speaker_parser 只兼容旧记录/旧模式。

session_snapshot 至少包含当前公开场景、角色、已知线索/物品、当前请求状态、待检定/待选择、事件游标和 server_capabilities。前端不在结构化协议不可用时偷偷退回文字；显示版本不支持并保留草稿。

### 5.3 请求、命令与去重

玩家 request_id 表示一次意图，主持 command_id 表示一次副作用，check_request_id 表示一次被请求检定，不能混为同一个 ID。一个玩家意图可导致多个命令。

去重键绑定 world、ID、身份和载荷摘要；重复同内容返回旧结果，同 ID 不同内容拒绝。Agent 重试不能依赖供应商 tool_call_id（重生成会变）；harness 为已计划步骤保存稳定 command_id。数据库唯一约束做最后一道防线。

## 6. 后端领域命令与持久化

公共应用层负责命令授权与事务，human HTTP/WS 与 Agent tool adapter 都调用它。逐项从 registry 提取业务逻辑；领域函数不能反向依赖模型。禁止新增万能 `execute_tool(name,args)` 公网入口和任意 state_set。

最小命令集：move_party、request_check、resolve_check、present_information、grant_clue、use_item、transfer_item、adjust_stat、advance_time、publish_message、resolve_intent；辅助查询为公开候选、主持场景详情、规则/模组资料检索。每个命令显式说明权限、参数、前置条件、状态变化、公开事件和失败码。

现有模组 flag 条件、战斗资格等规则保留为可解释策略；人工例外采用专用留痕命令，不能绕过访问隔离或幂等。新模式中的重复检定依据持久 check request、目标 ID 与做法/条件关系，而非只比较玩家句子。

物品与线索增加稳定 ID：旧字符串库存迁移为实体/堆叠项；保留原标签、数量、旧值映射和 schema_version。迁移一次生成并保存 ID，不能每次读取重新计算；重名物品必须区分。旧前端使用兼容投影，新操作只接受已授权稳定 ID。快照恢复保留同一分支内标识，跨世界所有请求仍校验 world_id。不得顺便重置进度或覆盖自定义场景。

建议新增或扩展持久数据：player_requests、game_commands、check_requests、待发布事件、主持控制权；采用现有存储风格，精确表名由后端在协议阶段冻结。知识分发需要接收者授权记录；不能仅新增一个全局 clues_found 就宣称私发已支持。

### 6.1 新模式的提交边界（必做）

每个副作用命令或固定原子组合，在一个事务中写入状态、执行结果、所需快照/恢复标识、待发布事件。提交成功后才对外发权威结果与图片；断线用事件游标补发。复用 turn_events 必须确认能承载多命令且不会被失败回合删除，否则增加独立命令事件表。

不要跨整个模型生成周期持有数据库事务或世界锁。读取最新状态、规划、短事务校验并执行；模型思考期间世界变化则重判。

后续模型失败不回滚已经宣布的命令。一次主持回应可记为 partial/paused，恢复从最后完成命令继续，不重新执行。不能直接在旧 turn_cache 里调用 flush_turn 冒充解决原子性；structured_v1 使用独立命令提交路径，旧路径保持隔离。

固定组合示例：物品消耗+治疗结果+相关事件原子提交；grant_clue+对应授权图片展示可原子提交。若规则规定检定前支付代价，应先提交明确代价与待检定，再等待玩家。

### 6.2 待检定生命周期

pending → resolved / declined / cancelled / expired。检定创建即持久化，保存角色、技能、目标、参数、规则版本及依赖条件。执行时复核角色控制权和相关条件；无关聊天不使检定失效，场景/物品等相关条件变化则失效并由主持重新请求，不能偷偷换参数。

超时不默认掷骰；多人可由主持取消或延期。秘密检定由获授权主持发起，结果仅按权限投递。断线、重启、接管均可恢复未完成检定。

## 7. Agent 工作流与提示词设计

循环：观察请求和授权状态 → 判断交谈/操作/澄清 → 提出明确命令或发言 → 读取已提交结果 → 继续或等待玩家。不要求暴露思维链；只保存简洁决策类型、工具调用、依据引用和停止原因。

模型可以先叙事铺垫，再调用工具，再根据结果叙事。但工具前不能宣布已移动/已取得/已掷骰等未发生事实；纯气氛与回应可以先发。工具请求参数必须完整校验，不能边解析半截 JSON 边落账。

结构化按钮中的 action kind、对象 ID 和数量必须保留，模型不擅自替换。若做法不合理，给出原因或可执行替代；不能修改目标后当作原请求成功。

关键 system 约束模板（后端结合实际命令 schema 实现）：

> 你是本场游戏的守秘人。玩家结构化请求表示尝试意图，不是成功事实。先检查场景与对象，决定直接处理、请求检定或澄清。游戏状态只由授权命令改变；叙事不能代替命令。工具返回已提交结果后才能断言相应事实。需要玩家选择或掷骰时创建待办并停止。本次回应结束前明确处理了什么、尚待什么，不代替玩家继续新的关键行动。
>
> “想看某物”“可以去吗”不自动等于出发；明确前往按钮、明确出发指令或对已约定目的地的确认才支持移动。抵达与检查分开。出示不是赠送；说明线索不等于持有原件。普通骰不能用于刷取检定结果。私密资料只用于主持判断，不直接发布给玩家。

harness 设置每次响应工具上限、模型调用/Token/费用预算、无进展检测和取消信号。超限进入 paused，保留已提交结果与待办，不静默兜底执行猜测行动。Agent 上下文包含命令结果、未完成请求、公开历史和授权知识，不要求整包模组全部注入。

自动化策略：manual（人类主动执行）、assisted（候选待批准）、automatic（Agent/明确作者规则）。对同一效果只有一个执行所有者，禁用新模式旧关键词自动发放与移动，防止双结算；不能无差别删除危机、战斗、时钟等必要规则。

## 8. 前端模块与接口适配

前端职责：明确操作对象、展示状态、收集玩家回应、按已授权事件渲染。不会决定是否成功，不发送伪骰点，不根据 NPC 文本猜状态。

建议新增 action-request store、pending-check store 和统一 command transport；具体命名可遵循现有风格。`ws.ts` 与 `room-ws.ts` 仅适配连接，事件归并/去重和状态更新共用一处实现。复用已有 scene-store/场景指示器，避免第二套位置源。

改造 InvestigatorPanel / PanelActionDialog；新增 DicePanel、CheckRequestCard、MoveActionDialog、ActionStatusCard 和最小 KeeperConsole。完整人类台提供场景/NPC/资料选择、明确发言、线索图片分发、检定、HP/SAN 和时间操作，以及待处理行动列表。

新场景/线索/物品更新只应用当前 world 的有效 revision，事件去重按 event_id。公开聊天事件可在相同 revision 下多次出现，不能因为 revision 相同全部丢弃。切换世界清理队列与草稿绑定，旧回调不能污染新世界。

所有按钮具备键盘可用性、明确禁用原因、提交中防重复和错误后保留草稿；不能用只禁按钮代替服务端幂等。桌面与窄屏实测，遵循现有 UI 按钮验收约定。

## 9. 人类主持与无模型闭环

human 创建房间时不要求模型 Key，也不要求主持认领调查员。玩家请求进入主持待办；主持直接选择允许、拒绝、检定或自定义解释，通过公共命令完成操作。人类选择 NPC 身份发言不经过 speaker_parser。

第一版一位活动 keeper、两位玩家、共享场景。人类用界面完成法伦委托 → 停尸房 → 展示证明 → 检定 → 检查遗体 → SAN → 保存恢复。至少一次私发线索给甲，乙不得看到。整个过程禁止模型网络调用，不能用 mock 模型生成主持内容冒充无人类台。

assisted 与 agent 必须在该闭环稳定之后接入相同服务。辅助建议批准时复核当前状态；接管在命令事务边界发生，旧 epoch 拒绝迟到工具。

## 10. 双方任务分工与文件所有权

| 负责方 | 所有权 |
|---|---|
| Kimi：后端与协议 | src/、server.py、migrations/、schemas/、后端 tests、Agent 提示词、协议说明与 JSON fixtures |
| zcode：前端 | frontend/src、frontend/e2e、前端组件/状态/传输/样式/测试、界面截图 |
| 联合集成 | 协议差异、fixtures、完整 E2E、交付记录；后端调整服务，前端调整调用，禁止跨界偷偷绕过 |

同一工作区不要同时改同一文件；建议各自在冻结基线上用独立工作树/分支，通过协议提交衔接。现有多人 E2E 若双方需要修改，指定前端负责，后端提出服务启动与 fixture 需求。

前端可用 fixtures 先做组件，不可将 mock 通过当作后端功能完成。后端可以先完成无 UI 集成测试，但最终必须与真实前端联调。前端实现前复用仓库已有 UI 技能与主题约束，无需另行生成美术资产。

## 11. 里程碑与依赖

### M0：基线和协议冻结

后端输出 protocol v1 schema、事件/请求 fixtures、错误码、权限矩阵、稳定 ID 迁移策略、提交边界设计。前端确认 UI 所需字段，尤其公开目标候选、物品可用操作与待检定恢复。记录现有工作区改动归属。

验收：双方用同一批 fixtures 做校验；确定 execution_profile 与 capability 协商；不开始两个不同版本的 API。

### M1：公共命令与人类主持最小闭环

后端完成身份、命令、事件、稳定对象 ID、待办与无模型会话；前端完成基本 KeeperConsole、玩家结构化请求、检定卡、场景显示与存档恢复。

验收：三客户端无模型调查流程成功、私发隔离、提交失败无权威事件、重试不重复结算。此阶段不以 Agent 试玩替代。

### M2：玩家交互完善

完成出示三种方式、道具使用/数量、前往、普通骰、孤注一掷入口、动作状态与错误恢复。补齐本地和云端入口、窄屏、键盘操作。

验收：按钮实际发送结构请求；所有字段由权威数据回填；不会回到 buildPanelActionText 权威路径。

### M3：Agent 决策与叙事循环

后端将 Agent 接入命令服务、资料检索、待检定暂停恢复、预算和人类接管；前端提供辅助草稿批准/拒绝、暂停和接管反馈。

验收：表达意愿不会自动移动，明确前往可以执行；工具失败不叙述成功；掷骰前停下；已提交动作不因模型失败回滚。

### M4：兼容、故障与真实模型验收

冻结整合提交，跑后端/前端/协议/E2E 全量与场景移动、线索、战斗相关项目要求。真实模型验收使用独立测试世界，遵守既有额度授权范围；没有适用授权则先完成离线工作，不使用生产存档或平台 Key。

记录旧模式与新模式差异和实际未通过项，不用换 harness 输入掩盖真实拒行。通过后由用户决定是否进 staging/正式发布；不自动上线。

## 12. 联合验收矩阵

| 类别 | 必测行为 |
|---|---|
| 意图 | “想看看尸体”先回应；明确前往移动；“那就过去”正确承接；否定/假设/谈论不移动 |
| 出示 | 知道但无原件可说明；有原件可展示但不转移；不存在或无权对象拒绝 |
| 道具 | 正确目标/数量；检定前后代价符合规则；重复点击不双扣；失败保留真实代价 |
| 骰子 | 普通骰无剧情效果；指定玩家可掷；别人代点拒绝；结果保存后动画；重复响应返回原结果 |
| 检定 | 相关状态变化作废；刷新恢复；取消与超时不自动掷；孤注一掷受规则约束 |
| 移动 | 成功才更新公开场景；拒绝保持原地；抵达不检查；新模式无关键词自动移动 |
| 隐私 | keeper/owner 区分；甲私有乙不可见；实时/恢复/历史/素材/导出一致 |
| 并发 | 请求 ID 同载荷去重、异载荷拒绝；revision 冲突；角色控制权变化；接管旧 epoch 拒绝 |
| 持久化 | 提交前故障无公开权威结果；提交后推送失败可重放；模型失败恢复不重执行 |
| 生命周期 | 无 Key 人类开局/续团；模型故障不影响主持台；存档分支恢复待办并绑定新世界权限 |
| 兼容 | 旧快照 ID 迁移保留进度；自定义内容不覆盖；旧模式原回归通过 |
| UI | 桌面/窄屏/长地名/长道具名；焦点、禁用原因、草稿保留、无横向挤压 |

验收产物：冻结 SHA、命令与事件示例、迁移前后摘要、自动化测试日志、三客户端截图/录屏、故障注入结果、真实模型请求与状态对照（脱敏）。分别标明 mock、真实服务、真实模型，不混报。

## 13. 风险与处理原则

- 最大成本是提交边界与生命周期重构，不能当作按钮增补。优先交付 M1 再展开全部工具。
- 不承诺结构化请求让 Agent 永不误判；拒绝原因、可执行替代与接管仍必需。
- 已公开秘密无法撤回；素材必须在授权和提交成功后发布。
- 模板刷新覆盖自定义内容是已有风险；新世界创建能力必须使用覆盖层或明确保护，不继续往会被替换的目录塞玩家创作。
- 规则自动化与主持操作必须防双执行；每个迁移命令明确旧自动触发是否关闭。
- 回滚程序版本不代表能直接降级数据库。迁移采用扩展兼容策略，发布前说明旧版本读取边界和恢复方案。
