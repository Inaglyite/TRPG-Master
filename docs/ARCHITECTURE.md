# 架构：跑团平台与 Agent harness

现行入口，整理于 2026-10-10；产品基线 `2b66a582`。本文件描述边界，发布及实际验收范围由[状态与限制](STATUS.md)单独维护。较长的历史实现资料见[归档入口](INDEX.md#归档资料)。

## 1. 产品与设计原则

平台同时服务人类守秘人和 Agent 守秘人。玩家通过按钮提交明确对象的操作意图，也可以自由说话；主持判断情境、请求检定、调用命令并叙事。服务端负责权限、确定性计算和持久化，前端只展示公开投影。

- 结构化按钮不能先拼成句子，再交关键词解析器决定效果。
- 意愿不等于执行，出示不等于赠送，抵达不等于调查或获得线索。
- 过渡是正常叙事与自由回应：需要玩家决定时真正停下，而不是播放固定提醒后继续替玩家行动。
- 人类和 Agent 复用领域服务；模型输出不是权威事实。
- 同一效果只有一个执行所有者，不让新旧引擎同时结算。

## 2. 两条执行路径

```text
Browser / Electron → React + Zustand → HTTP / WebSocket
                         ↓
          FastAPI + 身份/世界/房间权限
                         ↓ execution_profile
          ┌──────────────┴────────────────┐
       legacy                       structured_v1
 GameApplication                    StructuredGateway
 GameEngine / LangGraph              StructuredPlayService
 裁决 + 旧工具管线                      ↑ 人类 / assisted / Agent runner
 turn_cache                         逐命令短事务
 TurnJournal 整回合提交               状态 + 命令账本 + outbox 同事务
          └──────────────┬────────────────┘
                    SQLite / PostgreSQL
                         ↓
                  有权限的事件与快照 → UI
```

`execution_profile=legacy|structured_v1` 决定执行路径；新模式的 `keeper_mode=human|assisted|agent` 决定主持方式。本地/云端、单人/多人是另两个维度，不等于运行模式。

legacy 保留原有文本裁决与确定性后备。structured 不因协议或模型失败静默返回旧路径。旧模式通过的战斗、结局或主线测试，不自动证明新模式覆盖同样玩法。

结构化游戏时间通过 `src/structured/game_clock.py` 提供只读公开投影：快照和
时间/抵达事件只带已结算累计分钟数，不带案件时钟、NPC日程或截止条件。
客户端显示在场景旁与主持推进时间表单；未知不冒充0、断线显示上次记录，
读档按快照覆盖、换世界清空。不从叙事中的日期/跨度提取，不跟随真实时钟。
时间命令现将类型化 `activity` 与自由 `reason` 分开；省略类型按 `wait`，
非法显式类型在写入前拒绝。只调用既有时间规则，不改作者阈值/余量/上限。
旅行、检定、战斗的计时不代替其执行命令，也不重复结算其他命令已扣时间。
时间型案件时钟变化和命令在同一事务；公共投影不暴露时钟身份。
legacy主线已完成独立真实模型兼容性验收，不将该结果或无模型浏览器验收冒充structured Agent完整主线通过。

作者发现与实物取得由 `src/structured/discoveries.py` 核验：明确catalog ID/
规则序号/发现者/成功检定，信息发放和实物取得分开；稳定库存及取得账本随
世界状态保存，拒绝和outbox故障共同回滚。作者前置条件使用既有模组列表
语义，不匹配玩家文本；历史无物品绑定时由人类主持明确核对适用性。
`keeper_progress.py` 只提供主持专属作者目录和案件时钟；`execution.py` 在
领域命令前后比较投影，实际变化才发私有更新。嵌套草稿按子命令发布，不发
重复外层更新；玩家公开分钟投影和已获授权线索列表保持独立。
整队移动成功时只补已访问场景键，不生成legacy随机遭遇历史；同一提交边界
使失败移动、读档与分支不会留下未来访问记录。

人类主持的独立普通骰由 `src/structured/keeper_dice.py` 复用受限骰式/RNG，
服务层负责短事务、当前授权、原操作者查重；角色控制权与主持权分开。
不改变世界JSON/游戏revision/技能/伤害/时间；审计记录与事件原子提交。
可见历史从当前世界的outbox读取并在SQL层过滤，不从永久幂等账本取未来
结果，所以同revision的读档也不复活后掷的骰点。分支不复制普通骰历史。
前端紧凑档案夹表单与纸质收据只显示服务端结果，不本地掷骰或推测成败；
收据只作随机参考，不能替代玩家的待检定/战斗响应。Agent/辅助草稿禁止调用。

`src/structured/rate_limits.py` 为两种主动普通骰提供账号级、跨世界的
60秒限频（默认30次），不混入生成回合日额度或正式检定/战斗骰。授权、
幂等查重和载荷校验先行，再占额度/RNG；失败回帧不产生骰点或状态改变。
单调时钟、线程锁、有限账号键并清理过期项；不驱逐尚有效的账号来放行
新请求。当前仅单进程保证，重启会重置，多worker必须先换共享后端。

## 4. 权威状态与事务

| 数据 | 存储/所有者 | 非权威替代物 |
|---|---|---|
| 当前世界事实 | `world_states`；按模式由 store 或命令服务写入 | 叙事、摘要、人物记忆 |
| 世界模式/成员/控制关系 | `worlds/world_members/world_investigators` | 前端自报身份 |
| 旧回合与恢复 | `turns/turn_events/snapshots/save_slots` | 新命令游标 |
| 新请求/检定 | `player_requests/check_requests` | 行动已经成功 |
| 新命令/事件 | `game_commands/event_outbox` | 模型建议或发送成功 |
| 主持控制权 | `keeper_control` | 房主自动拥有主持权 |
| 当前交互/新记忆 | `interaction_threads/character_memories` | 执行授权/世界真相 |

legacy 的 mutation 可先进入 `turn_cache`，最终由日志服务与状态一起提交；流式展示不等于持久提交。structured 每条命令短事务写状态、命令结果与 outbox，提交后投递；模型中途失败不回滚已提交命令。记忆派生在提交后独立执行，失败可补建，不反写事实。

请求、命令、检定、交互线程使用不同 ID。重复同一操作复用同 ID/载荷；同 ID 不同载荷拒绝。`revision`、世界事件 `sequence`、`event_id` 不可互换；聊天事件可能不推进 revision。

### 结构化战斗与结案的共享边界

直接主持命令与人工批准的辅助草稿都经 `src/structured/execution.py`；
不得绕过同一终态检查、库存结算、角色投影和结局目录刷新。旧战斗规则仍
在 `src/gameplay/combat.py`，新协议不复制一套骰点或伤害算法。

- `combat_flow/pvp_flow` 保存明确决定和准备；玩家本人响应，双方对抗先分别
  同意/防御/准备再同事务结算。准备探针无骰源；原请求与执行凭证分开。
- `item_registry` 的持有人、数量和稳定编号是库存正本。`combat_weapons`
  只向旧规则提供选定件的临时视图；`combat_inventory` 按实际凭证精确扣弹。
  同名枪不靠正文辨认；堆叠源编号和使用件编号可不同。
- 角色查询沿用活动 `pc` 与非活动名册的既有所有权；`adjust_stat` 同步名册
  和战况、撤销旧准备。确认/执行再次检查角色和参战投影，不能靠缓存复活。
  数值调整不自动移除伤势。完整角色状态只给本人/主持，公共战况脱敏。
- `conditions.record_condition` 是有依据的人类专用状态记录，不是治疗规则。
  状态枚举、严格布尔前值及世界revision共同校验；不改HP、不解除死亡、
  不清其他伤势。实际变更共用战况同步/授权撤销，无变化只留命令回执。
  `ConditionRecordReference` 展示主持私有角色与冻结核对值，变化需人工重新核对。
- `rulings` 是人类有依据的已声明状态裁定，Agent不能借此补条件；作者结局
  目录仅主持可读，准备不结算。`case_closure/case_characters` 分别负责原子
  结束剩余工作、固定本人结案卡面；账号另存/导出不重复发奖励或覆盖原卡。
- structured人物/线索/位置不接受迟到的 legacy `character_state/state_data`；
  保持两条投影链互斥，避免重连后空旧响应覆盖新快照。

功能与验收范围分别看 [协议](PROTOCOL.md) 和
[扩展实现契约的归档入口](INDEX.md#归档资料)，
不能据这里的模块描述宣称整个新模式或真实模型已验收。

## 5. 暂停、重连、读档、分支

云端单人结构化读档由 `room_restore` 控制生命周期，复用
`restore_structured_save`，不是放开多人 `save_load`。唯一房主/成员/认领
在同事务复核，严格 revision CAS；回滚、授权作废、主持 epoch 和内部
幂等凭证原子提交。提交后退役旧房间、关闭全部同主标签页（4413）、从
同世界重新加载。网关在取得世界锁后再次检查旧房间是否退役，拒绝排队的
旧帧；旧 Agent epoch 即使恢复到相同 revision 也不能继续落账。
前端清旧运输队列/游标/投影，但保留未提交的个人笔记。早于人物就绪或角色
关系不兼容的存档明确拒绝，不现场造角色或治疗。

分支认领语义按执行配置分开：legacy 的 claim.id 随行迁移；structured
按稳定 character_key 识别、各世界拥有独立认领副本，切指针不搬行。混合
执行配置拒绝切换，不通过删除重复认领掩盖唯一约束问题。

结构化单人开局在真实调查员与稳定库存物化后更新自动槽位，再宣布playing；
存档失败保留lobby并给出可重试拒绝，不显示虚假的已开局快照。重复开局或
普通重连不更新自动槽位。旧早于人物就绪的存档仍拒绝，不通过迁移补人物。
时间线切换/建分支成功后，在释放控制锁之前标记旧运行时退役；HTTP和WS
沿用同一受理守卫，广播/拆连接之间等待的旧帧不能继续写父世界。

- 普通重连：恢复当前已提交状态和待办，不取消玩家尚未回答的决定。
- 正常叙事等待：保存尚未执行行动、已告知事项与交互目标，runner 结束，玩家自由回应。追问完成不等于原行动完成。
- 主动读档：structured 使用专用 reconcile，未决请求置失败、pending 检定作废、开放线程取消，并清理/修正未来记忆与事件；不是完整恢复当时交互快照。
- 分支：legacy 从完成回合分叉；structured 从当前已提交状态分叉，可用 `expected_revision` 钉住分叉点，不伪造 turn ID。新世界不继承活动控制权和原 outbox。
- 模型不可用/预算耗尽：明确暂停及原因，保留已提交结果，允许合法接管；禁止永久 loading 或自动改用平台 Key。

细节与信封见[协议](PROTOCOL.md)；相关数据清理只由对应生命周期服务执行。

## 6. 模型与主持模式

human 不依赖 Key；assisted 产出主持私有草稿，批准时复核生成版本，再在一个有界事务中执行建议命令和发布叙事，任一失败整体回滚；agent 使用受限命令循环，按预算与控制权停止。人类通过 `control_keeper` 显式接管、交还或重试暂停请求；接管不授予权限，仍须 `can_keeper`。

新 runner 当前通过 BYOK caller 请求 JSON 决策，再校验、执行命令，不直接复用旧 ToolRuntime。触发主要来自玩家行动与检定回应；普通骰和一般主持命令不自动推进剧情，`control_keeper: retry` 是显式恢复调度的例外，幂等重放不重复调度。并发到达请求、开场以及恢复后的调度覆盖应以测试证明，不能仅根据提示词推断。

BYOK 按本地或账号/世界作用域解析；云端由相应世界所有者的有效绑定供本场使用，不允许缺配置时回退共享平台额度。Key 不进入角色记忆、prompt、前端回显或日志。

## 7. 上下文、规则知识与记忆

### 7.1 游戏 Skill 与世界 pin

旧引擎的规则知识由 catalog、世界冻结的 skill pin/manifest 和模组正文装配。已 pin 的旧世界不能随磁盘更新静默换规则。项目开发者使用的 `.agents/skills` 与游戏中的 `skills/` 不同。

### 7.2 四层上下文

| 层 | 内容 | 注入原则 |
|---|---|---|
| 权威状态 | 当前地点、合法对象、已提交结果 | 当前任务所需部分可靠提供 |
| 当前交互 | 已讨论目标、未执行行动、已提醒条件 | 跨请求保留，不靠长期检索碰运气 |
| 近期对话 | 玩家与主持刚刚的交流 | 连贯、有界，保留指代 |
| 角色记忆 | 亲历、被告知、传闻、推测 | 按需查询，附类型与来源 |

新路径的 `_build_context` 组装快照、交互、未决请求、近期消息、角色记忆和运行结果；system 来自 `agent_prompts.py`。这不是旧 ModelSession 的完整历史，也不能假定自动继承旧模组/skill/Lorebook 注入。

### 7.3 按需知识与查询

旧 Lorebook 和 skill activation 是有门槛、有预算的知识选择。新角色记忆来自 `src/structured/memories.py`，支持提交事件派生、显式记录、替代更正与预算检索。当前检索有近期候选上限和相关度回退，不应宣传为精确语义搜索。

Agent 要知道上下文是局部注入：未提供不等于未发生，缺依据可查询，不能虚构；但工具是否能提供任务所需模组知识仍须查实际请求。主持知道秘密不代表其扮演的 NPC 知情。

### 7.4 摘要与来源

旧摘要是非权威连续性缓存；新记忆也不拥有世界事实。检索结果、规则 pin、当前交互与世界状态必须保持来源区别。提示词约束不能证明叙事绝无越界，真实模型表现单独验收。

### 7.5 旧 shadow memory 与新角色记忆

`src/ai/context/structured_memory.py` 和 `memory_fact_candidates/memory_facts` 是旧 H3 shadow 机制；`src/structured/memories.py` 和 `character_memories` 是新运行路径的角色记忆。二者不是同一接口，测试也分别为 `test_structured_memory.py` 与 `test_structured_character_memory.py`。

### 7.6 主持笔记、资料检索与可恢复压缩

`AgentKnowledge` 为 structured Agent/assisted 提供 `module/notes/history/receipt`
只读查询；角色 `memory` 查询仍沿用原接口。模组只接受注册表文档ID，不接受
模型文件路径；安装版本不符时明确拒绝。历史查询覆盖当前世界完整outbox与
分叉时冻结的 `branch_history_entries`，回执查询读取完整 `game_commands`。
返回字符页、来源ID、SHA256、是否读完及续读位置，不以截短内容冒充全文。

私有Markdown笔记存于世界JSON的 `keeper_notebook`，使用独立笔记版本CAS。
索引常驻、正文按需读；已引用的事件冻结到 `keeper_note_sources`，避免分支
复用事件序号改变旧出处。两者随存档和分支复制，角色记忆与玩家笔记继续独立。
人类主持从资料库“主持笔记”查看，用“更正这份笔记”准备带版本及出处的表单，
确认提交后才保存；不需手抄ID。自动摘要的 `harness-chapter-` 笔记更正只允许
人类主持；更正退出旧摘要的当前索引，保留原摘要与已复核来源，避免重新生成
旧结论覆盖主持意见。

近期对白按字符预算保留原文，旧对白转为带事件范围与检索入口的
`harness_checkpoint`；压缩不删除原始账本，不递归总结旧摘要。待办、交互、
世界事实始终单独提供，笔记/摘录不构成执行授权。Agent持久化检查点；assisted
只构造投影，批准草稿之前不改世界JSON。模型是否主动记笔记、选择正确关键词
仍受模型行为影响；原文持久化与可追溯不等于任何长度的团都绝不会答错。

`ReceiptCompactor` 保留近期12份原始回执，未压缩的
旧回执达到48份后，每运行最多整理一个阶段、最多16份来源及20000字符输入。
输入将命令与结果成对保留，保护 queued/processing/awaiting_player/paused 请求；
过去生成的摘要正文不再送入压缩器。模型输出分类事件/承诺/疑问/计划/推测，
每条引用真实回执；过大的来源只提供待回读指针，不允许据其生成事实断言。
`harness_chapters` 保存来源hash与语义摘要，`chapter_index` 索引常驻，正文由
`chapters` 查询续读。检查点不删原文、不改变规则revision，写入前复核控制权
与确切来源；源时间线已变化则拒绝。每次摘要调用占同一运行的模型/上下文预算。
辅助主持只生成预览，并在草稿前附带保存私有笔记；批准之前世界JSON不变。
已批准摘要笔记的正文在人工资料库显示为可读条目；手工更正的来源不重新压缩。
发言回执默认给指针；其他回执自动注入有总字符预算的实际结果，完整载荷与
事件按需读取，避免与近期对白反复重复。笔记满额时不附加自动摘要笔记，避免
阻断正常玩法草稿；原始账本仍可检索。模型与查询预算拒绝明确回喂。

查询结果必须在下一次决策中消费。成功回执提供完整结果或明确的全文读取
入口；拒绝反馈包含命令ID、错误码和未执行状态。读档后保留命令幂等账本，
将废弃时间线标记排除出当前检索；旧ID只返回标记过的缓存，不再执行。请求
已结束且没有排队工作时停止，不再额外生成运行报告或查询无关备忘。

上下文窗口默认262144 tokens（256K），可由环境或模型服务的显式窗口配置覆盖。
容量按单次实际请求检查并预留输出，legacy预检与structured BYOK调用都尊重所选
模型配置；未填写模型窗口时使用全局默认。Agent不再按重复发送的输入/输出累计
60000估算token来限制整个运行，仍保留每运行6次模型调用、12条命令与8次查询。
旧历史压缩、阶段记忆与完整原文回读继续工作；增大默认窗口不改变供应商实际容量。
参考 [Codex配置说明](https://developers.openai.com/codex/config-reference/) 对模型窗口
和自动压缩阈值的区分，以及 [Claude Code上下文说明](https://code.claude.com/docs/en/how-claude-code-works#the-context-window)
按当前占用清理旧工具输出、压缩历史的方式；编程Agent没有统一的256K默认值。

新存档在行锁内冻结回执成员与事件摘要，内部游标不进入公开存档列表。
切换多份存档时恢复确切成员，不能只比较可能复用的revision/sequence。
`command_event_receipts` 随命令、状态和outbox同事务保存不可变事件；批准草稿
的每条命令载荷、结果和实际叙事均保留。分支复制原始事件，缓存重放仍不重发。
已从outbox回滚的公开/私有发言可从该存档有效的事件回执重读；
另一时间线的同序号事件不会进入当前历史检索。
`command_request_receipts` 在命令执行前冻结关联玩家请求的完整原始载荷与当时状态，
随回执复制到分支；已完成请求不重新入队，仍可作为阶段记忆的来源。请求载荷
明确标为主持私有、不是公开发言、不是已执行事实，不能从计划推断实际行动。
旧命令缺事件或请求档案时分别明确标记不完整，不伪造已丢失记录。新增表由
迁移0020/0021建立，桌面旧库接管清单同步维护，保留旧行与幂等键。

读档递增私有 `harness_timeline_generation`，独立于可复用的revision。
辅助查询跨读档立即放弃旧反馈；生成及批准草稿均核对代数。Agent每次调用前后
复核控制权，避免接管后继续读取私有上下文或执行旧决策。

设计参考官方 [ZCode记忆实现](https://github.com/zai-org/ZCode/tree/aac4755666d09fdcd70272fcf063c077a639015f/apps/zcode-cli/packages/core/src/memory)
的索引/正文分离，以及 [DeepSeek Harness压缩实现](https://github.com/deepseek-ai/deepseek-harness/tree/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/compaction)
的近期保留、检查点与完整工具配对原则；本项目使用世界权限和结构化命令，
没有赋予跑团Agent通用bash或任意文件编辑能力。

## 8. 前端、权限与进程边界

React → typed transport → HTTP/WS；Zod/协议校验 → Zustand → 组件。`structured-transport.ts` 统一两类 WS 的发帧、重试和事件处理，`structured-effects.ts` 负责显示投影。新消息使用显式 speaker，骰子动画不决定骰值，场景栏不从叙事猜位置。

角色权限由服务端解析。owner、player、viewer 与 can_keeper/调查员控制权分开；私人内容在实时帧、快照、重放和模型上下文中分别检查。兼任 keeper 的人本来能看主持资料，不能把其连接当普通玩家隔离验收。

房间实例、Agent 活动任务和部分锁是进程内状态。当前单 worker 假设下的测试不能证明多进程/多副本安全；扩容前先设计世界归属和事件调度，不直接增加 worker 或套 K8s。

## 9. 扩展方式

先定义用户行为、运行模式、效果所有者、权限、事务及恢复，再改 schema/handler/提示词目录/前端 builder，并加正常与拒绝对偶。新增迁移同时核对打包接管表集；新增事件同时核对外层白名单、实时投影与快照恢复。

跨模块任务须给出唯一负责人、文件边界、冻结 SHA、fixtures、验收与交接对象；流程见[开发与协作](DEVELOPMENT.md)。运维与发布授权见[运维](OPERATIONS.md)。架构检查通过仅证明已有静态门禁通过，不代替完整审计。
